# NitroBison personal cloud sync and portable files

NitroBison works locally without a cloud account. For ordinary desktop use, the simplest way to get real Markdown files into personal Google Drive or OneDrive is the provider's installed sync client plus explicitly enabled **Markdown saving to a linked local folder**. No OAuth registration is needed for that route. The separate API connectors below are optional, **online, manual and personal-vault only**: connecting authorizes access but does not itself upload notes; use **Sync cloud** to merge and save a JSON snapshot. API sync covers the **whole personal vault, including every project**, regardless of the project currently open. Team workspaces are retired; their implementation and isolated-data recovery notes are preserved in [the repository reference](../reference/team-workspace/README.md).

Access tokens, authorization state, PKCE verifier and cloud merge bases live only in browser memory. Reloading, closing the app or disconnecting requires connecting again. No client secret, API key, refresh token, service-account credential or provider token belongs in NitroBison's source, configuration or local storage. A client ID is public registration metadata, not a credential. Disconnect clears NitroBison's token; it does not sign out the provider or revoke consent. Revoke consent separately in your Google/Microsoft account settings if required.

## Easiest personal setup: desktop and a provider sync folder

1. Install the NitroBison desktop app and either [Google Drive for desktop](https://support.google.com/drive/answer/10838124) or the [OneDrive sync app](https://support.microsoft.com/en-us/office/sync-files-with-onedrive-in-windows-615391c4-2bd3-4aae-a42a-858262e42a49). Sign in to the provider's client with your intended personal account. You do **not** need Google Cloud, an Entra app registration, a client ID or a client secret for this route.
2. In your file manager, create a dedicated empty folder inside the provider's locally accessible sync folder, for example a `NitroBison` subfolder. Make sure that directory is available on this computer; a browser-only cloud URL or an unavailable online-only directory is not a local destination.
3. For a new desktop vault folder/project, use **Choose parent folder** while creating it: NitroBison creates the named folder inside that selected parent and enables Markdown saving there. Without a selected parent, new folders instead save under the private NitroBison app-data `Markdown` directory; that is not a provider sync folder or a cloud connection. For an existing vault folder, its frontpage or **Show folder path** chooses the final destination directly; explicitly enable saving for old references. Read the writing disclosure before enabling it. An old saved path alone is **not enabled** and is not automatically moved into a child directory. Browser folder-name labels never enable desktop writes.
4. Edit or create a note in that vault folder and wait for the linked-folder save status. NitroBison writes `.md` files, preserving relative subfolders; a more specific nested linked folder takes precedence over its parent's destination. It does not import files already there or relocate the authoritative notes out of IndexedDB.
5. Use **Open folder** to inspect the actual files. Then check Google Drive for desktop/OneDrive's own upload status. **A successful local Markdown save is not proof of a cloud upload.** Uploads, account sign-in, online-only availability and provider conflicts are the OS client's responsibility. Connecting NitroBison's API account is unnecessary for this route.

Existing references from older versions were location labels only; that is why a previously selected directory can still be empty. They remain reference-only until you explicitly enable saving. Disabling saving, clearing a reference or choosing another directory leaves the old files in place. Local notes remain in the stable NitroBison application profile; do not clear app data to repair a missing folder or failed upload. Keep independent JSON backups, which preserve note IDs, timestamps and tombstones that Markdown files do not. Full filesystem conflict, recovery and profile-location guidance is in [the desktop guide](DESKTOP.md#local-folder-paths-and-markdown-saving).

This is an **outbound Markdown mirror, not a two-way filesystem vault**. External edits are not automatically imported. Different existing files and externally changed tracked files stop the affected save instead of being knowingly overwritten. Partial I/O failure can leave some files updated while local notes remain recoverable; inspect the reported path, preserve both versions and resolve the conflict deliberately. Do not edit the mirror from another app while NitroBison writes it. A provider client or another process can race local filesystem operations; no cross-process or cross-file atomicity is promised.

## Project and drive overview

The home page groups the personal vault into its actual top-level folders, including nested notes, and an **Unfiled pages** collection when root pages exist. These are navigation groups, not separate storage accounts or synthetic folders. Local storage remains available without a provider. Settings **Accounts** contains the Google Drive and OneDrive pages; there is no separate Connections subtab. A saved client ID means **configured**, not connected; reconnect to authorize a live session. Cloud storage applies to all personal projects together. Neither configuration nor a selected project creates a per-project cloud association. Provider logos are local assets.

Account authorization and folder status are separate. A live, nonexpired token and successful provider verification establish the current API connection; a path string or client ID does not. Google verification reads the authorized profile and canonical Herd-folder metadata without creating a folder. OneDrive verification requests `approot`, which Microsoft may create as an **empty app folder** on first access; **no notes or vault.json are uploaded until explicit Sync**. A missing Google folder is a truthful “not created yet” state, not failed sign-in. Provider folder metadata is not a full local filesystem path.

Only verified business Google Drive labels append **EA**; OneDrive and personal labels remain unchanged. Google classification uses profile `hd` metadata, not an email suffix or registration audience. OneDrive retains returned drive metadata for account-kind information without an EA label. Unavailable metadata stays unknown. Desktop references separately verify real local directories and trustworthy OS-client metadata; names and manually selected service labels are not authenticated provider access or proof of upload.

## Storage compatibility

NitroBison keeps the existing storage and authorization identities so the rename does not hide an existing vault. Google Drive continues to look up and create the historical **Herd** folder with the private property key `herd` and value `vault-v1`; its snapshot remains **vault.json**. Do not rename those identifiers as part of an upgrade. Existing OneDrive app folders remain tied to the same Entra registration, and recovery files keep the **herd-recovery-{UUID}.json** prefix. The OAuth callback path and `herd-oauth-callback` message type are unchanged. Keep your existing client IDs and registered origins/callbacks when upgrading; no data migration or account re-registration is required by the product rename.

## Host prerequisites

Serve at an HTTPS origin, or localhost for development. Open the installed PWA on that same registered origin. Preserve `/oauth-callback.html` and `/oauth-callback.js` as real static files, not SPA fallback responses. Allow popups. Cross-Origin-Opener-Policy must be `same-origin-allow-popups` rather than `same-origin`, or the provider popup can lose its opener. The callback sends its one-use code only to its own origin; the opener checks the exact popup window, origin and random state before using it. Microsoft additionally binds code redemption to a fresh S256 PKCE verifier.

For a custom CSP, allow:

- Google GIS script/frame/connect: `https://accounts.google.com`.
- Authenticated Google REST: `https://www.googleapis.com`.
- Microsoft token exchange: `https://login.microsoftonline.com`.
- Microsoft Graph: `https://graph.microsoft.com`.
- OneDrive preauthenticated download/upload hosts: `https://*.1drv.com` and `https://*.sharepoint.com`.

The connector accepts HTTPS OneDrive transfer URLs only in those last two domain families. It sends **no Authorization header or cookies** to them and suppresses referrers. This connector targets the global Microsoft cloud, not sovereign/national clouds. Do not proxy provider calls through the app's static host or record authentication codes/query strings in access logs.

## Native desktop authorization

The packaged desktop app starts and keeps its local vault without an account, OAuth registration or network connection. Cloud authorization is optional and opens the **system browser**, never an embedded sign-in window. Its packaged renderer uses the stable local origin `app://bundle/`; do not register that origin as an OAuth web redirect. Existing browser/PWA setup in the registration sections below stays unchanged.

Native sign-in uses a fresh random state and **S256 PKCE**, with a temporary listener bound only to IPv4 `127.0.0.1` on an operating-system-selected port. Its callback path is exactly `/`. The listener checks the expected Host header, method, path, one-use state and authorization code, rejects duplicate query fields and bounds request/header sizes. No callback page scripts, images or remote assets are loaded. The code exchange runs in the desktop main process against fixed official HTTPS token endpoints; there is no arbitrary network, filesystem or shell bridge. The renderer receives only access token, token type, expiry and scope, and revalidates the bearer token and required scope. Codes, PKCE verifiers and tokens are memory-only; refresh/ID tokens are discarded, not saved or returned.

Only one authorization can be pending. **Cancel**, closing the app or the five-minute authorization timeout closes the temporary listener and aborts an in-flight exchange. A provider denial, malformed callback, state mismatch, browser-launch failure or token-exchange failure also releases it. Browser cookies remain controlled by the system browser; disconnect does not revoke provider consent. Reconnect after reloading or reopening NitroBison. Authorization does not itself upload notes.

### Google native registration and existing web vaults

1. Keep the **existing Google Cloud project**, Drive API, consent audience and test-user configuration when adding native access for an existing web installation.
2. In Google Auth Platform **Clients**, create a separate OAuth client of type **Desktop app**. Put its **public client ID**, not the Web application's client ID or a client secret, in the desktop app. The web/PWA keeps its existing **Web application** client and exact Authorized JavaScript origins.
3. The native app requests `https://www.googleapis.com/auth/drive.file` plus the identity scopes `openid profile email`, uses `http://127.0.0.1:PORT/` as the loopback redirect, and exchanges its PKCE-bound code at `https://oauth2.googleapis.com/token`. The identity scopes support authorized profile/account-kind verification; they do not grant wider Drive access. The random port is chosen for each attempt; do not register `app://bundle/` or the web `/oauth-callback.html` for the desktop flow. Do not copy a generated client secret into NitroBison.
4. Review the intended account and explicitly sync only after deciding how to retain any existing web vault. No live Google account consent, Desktop/Web cross-client discovery or cloud writes were tested for this native implementation.

**Do not treat an empty native search as proof there is no existing web vault.** `drive.file` grants access only to app-authorized files; the canonical Herd marker is an application-private Drive v2 property. A Desktop client is distinct from a Web client even when both belong to the same project. Keeping the same project is necessary continuity guidance, not proof that both clients can see the same files and private marker in every account. Do not broaden to full Drive access, commandeer a same-named unmarked folder, or change the historical `herd=vault-v1` marker to work around missing visibility. Before intentionally creating a new native cloud vault, make an explicit user decision: cancel and export a JSON backup from the existing web vault first, or confirm that creating a separate cloud vault is intended. Restore/import the desired backup locally before syncing; retain the old cloud copy until continuity is verified. This avoids silently forking an existing web vault.

When native Google sync finds no visible canonical vault, NitroBison asks for confirmation **before creating any cloud folder or snapshot**, with **Cancel** selected by default. Cancel leaves the local vault intact. Proceed only after backing up any existing web vault and explicitly choosing to create a potentially separate cloud copy; the confirmation does not certify cross-client visibility or perform a cloud migration.

Google's current [installed-app protocol](https://developers.google.com/identity/protocols/oauth2/native-app) documents Desktop clients, public-client PKCE, system-browser loopback redirects and the optional token-endpoint client-secret field. Its [custom-properties guide](https://developers.google.com/workspace/drive/api/guides/properties) explains the app-private property boundary; neither a successful sign-in nor the same visible folder name proves cross-client canonical-vault discovery.

### OneDrive native registration and app-folder continuity

1. Open the **same existing Entra application registration** used by the web/PWA when accessing its OneDrive vault. Do not create another registration just to add desktop access: `approot` belongs to the registration, so a different application/client ID can lead to a different app folder.
2. Under **Authentication → Add a platform → Mobile and desktop applications**, add **`http://localhost`** for the system-browser flow. Keep existing **SPA** `/oauth-callback.html` redirects unchanged for web/PWA use. Do not place the native root callback under Web or SPA, enable implicit token grants, add a client secret, or add multiple localhost root redirects distinguished only by port.
3. Keep only the existing delegated `https://graph.microsoft.com/Files.ReadWrite.AppFolder` permission and the intended supported account types. The desktop app uses the same public Application (client) ID; tenant values are limited to `common`, `consumers`, `organizations`, a tenant UUID or a verified domain. It does not accept arbitrary authorities or sovereign-cloud endpoints. The personal/work-school compatibility caveats below still apply.
4. Native authorization requests `http://localhost:PORT/`, with `/` as the callback path, and exchanges the PKCE-bound code at `https://login.microsoftonline.com/{tenant}/oauth2/v2.0/token`. Microsoft ignores the ephemeral port when matching a localhost native redirect; the listener itself still binds only IPv4 loopback. `offline_access`, refresh tokens, ID tokens and broader file permissions are not requested or retained.

Microsoft's [desktop configuration guide](https://learn.microsoft.com/en-us/entra/identity-platform/scenario-desktop-app-configuration), [authorization-code protocol](https://learn.microsoft.com/en-us/entra/identity-platform/v2-oauth2-auth-code-flow) and [localhost redirect rules](https://learn.microsoft.com/en-us/entra/identity-platform/reply-url#localhost-exceptions) distinguish native and SPA redirects and describe PKCE and ephemeral ports. Local deterministic tests exercise the loopback/protocol boundaries with simulated token responses; they are **not live-account validation** of consent, organizational app-folder support or same-registration cloud continuity.

### Why OneDrive business support is not promised

Microsoft's [Graph app-folder article](https://learn.microsoft.com/en-us/graph/onedrive-sharepoint-appfolder) explicitly says app folders work across work/school and home accounts. Its metadata says `ms.date: 2025-03-14`, `updated_at: 2025-08-06`. The [OneDrive permission reference](https://learn.microsoft.com/en-us/onedrive/developer/rest-api/concepts/permissions_reference?view=odsp-graph-online), `ms.date: 2017-09-10` but `updated_at: 2026-05-14`, says the delegated permission is **only valid for personal accounts**. The newer [Graph permissions reference](https://learn.microsoft.com/en-us/graph/permissions-reference#filesreadwriteappfolder), `ms.date: 2026-09-14`, `updated_at: 2026-11-07`, lists personal-account consent without explicitly resolving work/school support; it labels the delegated permission preview. Page timestamps do not resolve this contradiction.

Keep personal accounts as the documented target. `common`, `organizations`, tenant UUIDs and verified domains select an authorization audience; they do not prove storage compatibility. ### Google audience and publishing limits

Google's [consent configuration](https://developers.google.com/workspace/guides/configure-oauth-consent) and [OAuth production guidance](https://developers.google.com/identity/protocols/oauth2/production-readiness/policy-compliance) distinguish Internal organizational apps from External apps. External Testing normally allows up to 100 listed test users; authorizations for Drive scopes expire after seven days. Publishing removes the testing lifecycle but is not a promise of administrator approval. `drive.file` is non-sensitive; that does not waive applicable branding, domain, privacy-policy or production requirements. Workspace administrators can restrict third-party app access. NitroBison does not use a service account, domain-wide delegation or an administrator's identity.

Google's [JavaScript-origin rules](https://developers.google.com/identity/protocols/oauth2/javascript-implicit-flow#uri-validation) explicitly exempt localhost IP addresses from the raw-IP and HTTPS restrictions. Register the exact origin shown in Settings, including its port. `localhost` and `127.0.0.1` still have different local vaults; do not change origins to troubleshoot without exporting JSON first.

### Dropbox implementation proposal

Dropbox is not in the provider selector and no authorization or sync code is installed for it. A complete addition would reach `src/cloud.js`, provider setup/state in `src/app.js` and `src/home.js`, the host CSP in `server/app.js`, cloud boundary tests and this guide. Reuse snapshot validation, the 10 MiB transfer limit, explicit personal-only synchronization and three-way conflict preservation; do not add a second merge system or backend proxy.

1. Register a **Scoped access → App folder** app in the [Dropbox App Console](https://www.dropbox.com/developers/apps). Enable only `files.metadata.read`, `files.content.read` and `files.content.write`; register the exact web callback. Use the public app key, never the secret or a generated development token.
2. Use the [authorization-code PKCE flow](https://docs.dropboxapi.com/dropbox-api/docs/oauth) with S256, random state, one-use popup validation and an online access token. Keep tokens/verifiers in memory, discard refresh tokens and reconnect after reopening, matching the existing providers.
3. Store `/vault.json` relative to the app-folder root. Load validated content with its opaque `rev`; upload existing content using `mode: { '.tag': 'update', update: rev }` and strict conflict handling. Create only with fail-on-conflict semantics, never overwrite or autorename a competing canonical vault. A revision mismatch must enter the existing reload/merge path, not blind retry. Handle cancelled consent, expired tokens, quota, denied access, corrupt/oversized snapshots, network-uncertain writes and provider conflict/rate-limit responses without losing the local copy. Do not add a background retry service.
4. Prove two-device conflicts, concurrent first creation, same-key cross-device continuity, read/write and revocation on personal and Business-member accounts before advertising support. Add only the documented Dropbox authorization/content/API domains needed by that implementation to CSP.
5. Follow the [Dropbox developer guide](https://docs.dropboxapi.com/dropbox-api/docs/developer-resources/developer-guide): a new app initially links its owner; enable additional development users explicitly. Development permits up to 500 linked users, but reaching 50 starts a two-week production-approval deadline before additional links freeze. Production approval, branding and privacy requirements apply to public distribution. Use the same key for the same app across platforms; self-hosted derivatives need their own registration.

The [Dropbox team-files guide](https://docs.dropboxapi.com/dropbox-api/docs/team-files) documents member App folders separately from team-linked tokens and admin impersonation. This proposal requests **no team scopes**, `Dropbox-API-Select-Admin`, `Dropbox-API-Select-User`, Full Dropbox or team-space access. Business administrators can [restrict integrations](https://help.dropbox.com/integrations/app-integrations). Organization-wide access would require a separately approved design, not an extra permission checkbox in this connector.


## Google Drive registration

For a private desktop user, prefer the [sync-folder route](#easiest-personal-setup-desktop-and-a-provider-sync-folder) unless you specifically want manual API JSON sync. Hosted/web/PWA users and desktop API users need their own public registration; NitroBison supplies no shared production OAuth client.

1. Sign in to [Google Cloud Console](https://console.cloud.google.com/) with the account that will own the registration. Create/select a project and enable **Google Drive API** under **APIs & Services → Library**. Keep the existing project/client for an existing vault.
2. Open **Google Auth Platform** (older consoles call this **OAuth consent screen**). Complete **Branding** with an app name, user-support email and developer contact email. For a personal Gmail account, choose the **External** audience, not Internal. Internal is for a Google Cloud Organization, not a shortcut for private Gmail use.
3. For a private trial, leave publishing status **Testing**. In **Audience → Test users**, add the **exact Google account you will use to connect**, including yourself even if you own the project, and save. An External Testing app with Drive access is limited to listed test users (normally up to 100); its Drive authorizations expire after seven days. Reconnect as required. Public publishing/branding requirements are separate from this private setup.
4. Under **Data Access → Add or remove scopes**, configure `https://www.googleapis.com/auth/drive.file` plus `openid`, `profile` and `email` (the console may display the equivalent `userinfo.profile`/`userinfo.email` names). These identity scopes let NitroBison verify the authorized profile, including Workspace `hd`; do not add full Drive access, service accounts or API keys.
5. For **web/PWA**, create **Clients → Create client → Web application**. Add the precise NitroBison origin shown in Settings to **Authorized JavaScript origins**, for example `https://notes.example.com` or `http://localhost:5173`. Origins have no path; scheme, host and port matter. Register each environment separately. Google's GIS token popup does **not** use `/oauth-callback.html` and needs no Google redirect URI or client secret.
6. For the **native desktop API connector**, instead create a separate **Desktop app** client in that same project and follow [native registration and web-vault continuity](#google-native-registration-and-existing-web-vaults). Do not put a Web client ID in the desktop app or register `app://bundle/`.
7. Copy only the public client ID into **Settings → Accounts → Google Drive**. Choose **Connect**, select the intended test-user account, inspect the app name and permissions, and grant consent only to your intended registration. A testing notice can be expected; if Google blocks access, fix the account/test-user, branding, scope or origin configuration instead of granting broader access or bypassing an unfamiliar warning.
8. Check the separately displayed account/folder result. Connecting verifies metadata; it does not create Google's Herd folder or upload notes. Use **Sync cloud** explicitly when ready. An expired session or reopened app requires connecting again. An unexpected empty desktop vault needs the native continuity warning, not an assumption that your web vault is gone.

NitroBison loads the official Google Identity Services script at runtime for web authorization. Drive access remains limited to files created/opened with that app's `drive.file` authorization, not all Drive contents. On explicit first sync it creates a visible **Herd** folder with the stable application-private marker described above and a regular **vault.json** snapshot. Existing unrelated folders named Herd are not commandeered. Use the same registered client ID across web devices to find the same app-authorized vault; the native client visibility caveat still applies. Google's [consent setup](https://developers.google.com/workspace/guides/configure-oauth-consent), [app-state/testing guide](https://developers.google.com/identity/protocols/oauth2/production-readiness/overview) and [client registration](https://developers.google.com/identity/oauth2/web/guides/get-google-api-clientid) document these registration boundaries.

### Why the Google connector uses Drive REST v2

GIS authentication is current; the storage REST API deliberately uses the still-published **Drive v2** `File.etag`, `title`, `items` and private `properties` representation. Drive v3 removed `File.etag`; substituting a v3 `version` read followed by a blind write would not enforce an atomic precondition. Updates use the v2 media upload endpoint with the loaded `If-Match` ETag and require the new ETag in the write response. Missing/unusable revisions fail closed. Do not migrate these URLs/fields to v3 without implementing an equally safe server-enforced concurrency mechanism.

Drive allows duplicate names. Simultaneous first-time creation may produce multiple `Herd` folders or `vault.json` files; NitroBison retains both and refuses ambiguous sync rather than picking a winner. Download every copy in Drive, preserve a local JSON backup, merge/restore the desired data, and resolve the duplicate remote copies manually before reconnecting. NitroBison never silently deletes a duplicate cloud copy.

### Read-only Google vaults

Google's `File.capabilities.canModifyContent` is the authoritative content-write capability. NitroBison requests it with the file ID and ETag during load and checks it again before replacing an existing snapshot. Explicit `false` exposes `connection.readOnly === true`; a missing capability is unknown, not proof of write permission. Unknown capability blocks replacement with `CLOUD_PERMISSION_UNKNOWN`; known read-only access blocks it with `CLOUD_READ_ONLY`. Ownership, the OAuth write scope, a generic 403, and successful reading are not substituted for this capability.

After a load establishes read-only access, **Refresh read-only vault** reads and merges remote changes without any upload. Local divergent notes and recovery copies are retained, and subsequent pulls use the actual remote snapshot as their merge base. A later refresh can discover restored editing permission. The interface hides Write/Split and note/folder mutation controls and shows the reason on the left of the reading toolbar or folder frontpage.

This connector stores one `vault.json`: its permission applies to the whole connected personal vault, not independently to each note or arbitrary Google Drive Markdown files. Connection/capability state is session-only. Before the first load, or after disconnect/reload, you are working with your editable local personal copy; this does not grant cloud write permission. OneDrive's current app-folder metadata does not establish an equivalent effective write capability, so NitroBison does not invent a read-only status for it. Provider-side authorization remains required for every write.

## OneDrive registration

1. First sign in to [OneDrive](https://onedrive.live.com/) with the personal Microsoft account you intend to use and ensure its drive is provisioned. The [desktop sync-folder route](#easiest-personal-setup-desktop-and-a-provider-sync-folder) needs no app registration. For direct API sync, open [Microsoft Entra app registrations](https://entra.microsoft.com/) in a directory where you have permission to register an app. A personal OneDrive account alone does not guarantee app-registration rights; if registration is unavailable, use the desktop route or have an authorized registration owner provide the public setup. Do not invent a client ID.
2. For a new registration, choose a name such as **NitroBison** and **Personal Microsoft accounts only** for a personal-only setup; choose the combined organizational-and-personal audience only if you intentionally need both. A single-organization registration will not accept ordinary personal Microsoft accounts. Keep the same existing registration when upgrading or adding desktop access, because it identifies the app folder. Microsoft's [supported-account-type guide](https://learn.microsoft.com/en-us/entra/identity-platform/v2-supported-account-types) explains the audiences.
3. For **web/PWA**, under **Authentication → Add a platform**, choose **Single-page application (SPA)**, **not Web**. Register the exact Settings callback, for example `https://notes.example.com/oauth-callback.html` or `http://localhost:5173/oauth-callback.html` for local Vite development. Scheme, origin, path and filename must match; register each environment precisely. Keep both `/oauth-callback.html` and `/oauth-callback.js` as real static files. HTTP `127.0.0.1` setup has the manifest caveat below.
4. For **native desktop**, add **Mobile and desktop applications** with **`http://localhost`** to the **same registration** instead; the runtime uses an ephemeral port and root `/` callback. This is not a SPA/Web redirect and must not be `app://bundle/` or `/oauth-callback.html`. A registration used on both platforms keeps both distinct platform configurations. See [native setup](#onedrive-native-registration-and-app-folder-continuity).
5. Under **API permissions**, use **Microsoft Graph → Delegated permissions → Files.ReadWrite.AppFolder**. Do not add application permissions, `Files.ReadWrite`, `Files.ReadWrite.All` or directory/profile permissions. Remove an unused default `User.Read` from a new dedicated registration if the portal added it; do not remove permissions needed by another existing application. NitroBison requests only its AppFolder scope. Tenant policy can require delegated-consent approval but never grants access beyond the signed-in user's drive.
6. Do **not** create/embed a client secret or enable implicit access-token/ID-token grants. Both clients are public, use authorization-code/S256 PKCE, and request no `offline_access`, refresh tokens, ID tokens, profile or directory membership.
7. Copy the **Application (client) ID** into **Settings → Accounts → OneDrive**, set **tenant** to **`consumers`** for the personal-only audience and connect. `common` is for the intentionally combined personal/organization audience; `organizations`, tenant UUIDs and verified domains are not personal-account workarounds. The API default remains `common`; single-tenant registrations should use their actual tenant ID.
8. In the provider window/system browser, choose the intended **personal** Microsoft account, inspect the app and delegated permission, and consent. Check NitroBison's verified account and app-folder result, then explicitly choose **Sync cloud** to transfer notes. The verification request may provision an **empty Apps/{Entra application name} folder** before Sync; this is not a note upload. Reconnect after reopening. If consent or `approot` fails, check provisioning/account audience and policy; do not broaden permissions to force success.

### Local `127.0.0.1` callbacks

Settings shows the current origin's exact callback. Microsoft's [redirect-URI restrictions](https://learn.microsoft.com/en-us/entra/identity-platform/reply-url#prefer-127001-over-localhost) recommend `127.0.0.1` but say the portal redirect-URI box cannot add an HTTP IP-loopback callback; its documented workaround is an app-manifest entry. If your manifest exposes `replyUrlsWithType`, preserve existing entries and add `{ "url": "http://127.0.0.1:5173/oauth-callback.html", "type": "Spa" }`, replacing the port with your actual port. See the [manifest reference](https://learn.microsoft.com/en-us/entra/identity-platform/reference-app-manifest#replyurlswithtype-attribute). Do not use `Web` or `InstalledClient` for this browser flow.

The Graph-format manifest instead exposes [`spa.redirectUris`](https://learn.microsoft.com/en-us/graph/api/resources/spaapplication?view=graph-rest-1.0); preserve the array and other platform fields. Microsoft's workaround page names `replyUrlsWithType`, not the Graph-format field. Saving an HTTP IP-loopback `Spa` entry through either current portal representation was **not tested here**; ask the registration owner to verify that Authentication lists the exact callback, or use a properly configured trusted HTTPS origin. Do not paste a legacy-only property into an incompatible manifest or claim a rejected save succeeded.

Do not silently switch to `localhost` as a workaround: it has separate IndexedDB and preferences. Download JSON on the existing origin before any intentional move, restore on the new origin, and keep the original copy until verified. Non-localhost IP loopback matching uses the exact registered port; register each environment precisely.

NitroBison uses `/me/drive/special/approot` (case-sensitive `approot`), giving it an isolated **Apps/{Entra application name}** folder in OneDrive. [Microsoft documents that the first approot request creates this folder if needed](https://learn.microsoft.com/en-us/graph/onedrive-sharepoint-appfolder); verifying a connection may therefore create the empty folder, but only explicit Sync writes **vault.json** or note snapshots. The folder name follows the registration, not NitroBison's displayed product name; keep an existing registration and app folder to retain access to its vault. Personal accounts are the documented delegated-permission target. Work/school app-folder support is **EA/unverified** because Microsoft's documentation conflicts, as detailed above; organizations may also block consent or lack a provisioned OneDrive. No wider permission is silently requested on failure.

### OneDrive revision safety and recovery files

Existing-file saves first create a UUID-named **herd-recovery-{UUID}.json** in the same app folder, containing the **new submitted snapshot**. This historical filename prefix is intentionally unchanged. Creation uses fail-on-name-conflict semantics and is never an overwrite. If preserving that version fails, canonical replacement does not start. Recovery snapshots are regular validated NitroBison JSON backups: download the desired file from OneDrive, keep another copy of your current vault, then use NitroBison's JSON backup restore action to recover it. They include tombstones, folders and note IDs.

Each existing-vault sync adds a recovery file and consumes provider quota. NitroBison does not automatically delete them. Export/download the revisions you need before manually removing older recovery files in OneDrive. A failed/interrupted sync may still have created a recovery file; inspect it before discarding it.

Replacement uses an upload session with the documented `If-Match` precondition and a conditional final upload. NitroBison returns a revision only after rereading the canonical snapshot and confirming its content and ETag. Microsoft documents the upload-session entry precondition, but its API reference does not establish a publication-time compare-and-swap guarantee for every account type/final-upload path. **Recovery copies preserve submitted NitroBison versions; they are not a claim of strict cross-provider atomicity against arbitrary external writers.** Avoid editing vault.json with other applications. A conflict or uncertain result is surfaced instead of blind retry; sync again to reload/merge. Live account-specific conditional-publication behavior has not been exercised without user-provided registration and credentials.

## Errors, conflicts and limits

- **401/expired/disconnected:** reconnect with the button, then sync. There is no background refresh or silent long-lived login.
- **403:** check the narrow delegated permission, account type, storage provisioning and tenant consent/policies.
- **404:** missing snapshot loads as empty remote state; a disappeared expected update is a conflict, not a request to recreate blindly.
- **409/412:** preserve local changes, reload/merge, then explicitly sync again. No automatic write retry is performed.
- **Popup blocked/cancelled or state mismatch:** allow popups and start a fresh connection from NitroBison. A mismatched state is rejected before Microsoft code exchange.
- **Google origin/client error:** correct the JavaScript origin and OAuth test-user/consent settings.
- **Microsoft CORS/redirect error:** check that the exact callback is registered under SPA, not Web. No secret can repair the wrong platform type.
- **Network failure/unknown write result:** the provider may have completed the write. Reload/merge before another attempt; keep local/recovery JSON copies.

Cloud JSON snapshots are validated through NitroBison's core validator before import and before upload, with a 10 MiB transfer limit. Malformed notes, folders, duplicate IDs and invalid timestamps fail instead of entering the workspace. A cloud snapshot is a regular JSON file, not end-to-end encrypted data: provider account access and applicable tenant policies still apply. Keep independent JSON backups.

## Markdown import and export

`importMarkdownFiles(fileList)` accepts a file picker/FileList or iterable, including a directory picker's `webkitRelativePath`. It imports `.md` (case-insensitive), preserves the entire supplied folder path including the selected root folder, reads file bodies without changing Markdown, and ignores other file types. A plain multiple-file picker has no directory information and imports into the root. Empty source directories and non-Markdown attachments cannot be reconstructed from a FileList. Imports assign fresh UUIDs; the workspace importer handles existing-title conflicts instead of silently replacing notes.

Paths must be relative slash-separated paths. Traversal, absolute paths, backslashes, control/reserved characters, trailing dots/spaces, Windows reserved device names, file/folder collisions, case-insensitive duplicates and Unicode-normalization filename collisions are rejected. No filename is silently sanitized into another. The complete input path set is checked before any file body is imported.

`exportMarkdownFolder(snapshot)` uses the browser's `showDirectoryPicker` with write permission. It preserves empty snapshot folders and nested Markdown files, excludes deletion tombstones and leaves unrelated destination entries untouched. It preflights every destination file: identical content is skipped; any differing existing file aborts with the conflicting path, without overwriting it. Choose a fresh/empty destination or move the existing file explicitly; there is no generic "overwrite all" confirmation. Pending files are checked again before creation and use exclusive writable streams. Browsers and operating systems do not provide a multi-file export transaction against unrelated native writers: avoid changing the destination during export. A device/permission error can leave a partial set of newly created files, but previously existing differing content is not intentionally overwritten.

Folder export needs a supporting Chromium browser on HTTPS/localhost. Other browsers get an actionable unsupported-feature error; **Download JSON** remains the complete portable backup option. Markdown export does not preserve note UUIDs, timestamps, tombstones or non-Markdown attachments; JSON does.

Folder frontpages use ordinary README notes. Existing `![Folder banner](data:image/...)` Markdown images remain bounded raster data, travel inside Markdown export/import and JSON snapshots, and remain preserved by the overview editor. Raw Markdown editors may show their base64 line; third-party Markdown readers vary in data-image support. Choosing or removing a new private banner never rewrites those existing Markdown images.

New banner uploads are re-encoded as JPEGs at up to 1280 pixels on the longest side and 512 KiB, then saved separately in IndexedDB as private personal-vault preferences for this browser/device. They override the README default on Home cards, folder frontpages and README reading views; a null override hides the image locally. They are excluded from note snapshots, Markdown/JSON backups and provider payloads, and do not consume the note/snapshot transfer limit. Read-only cloud access still allows these private preferences without editing cloud notes. Clearing browser data loses them; they are not a synchronized or portable settings backup. Retired team preferences remain untouched under their old identity keys.

In the **browser/PWA**, **Choose device folder** remains a location-label setting, not a filesystem-backed vault or automatic mirror. It uses [`showDirectoryPicker({mode: 'read'})`](https://developer.mozilla.org/en-US/docs/Web/API/Window/showDirectoryPicker) where supported, otherwise a [`webkitdirectory` input](https://developer.mozilla.org/en-US/docs/Web/API/HTMLInputElement/webkitdirectory). Only the selected root folder name is retained; no directory handle or full OS path is stored, and the app does not read file contents or sync that directory. The fallback needs modern input cancellation support; an empty folder without directory-entry metadata cannot supply a name. Cancel/error leaves the label unchanged. Native desktop separately supports [explicitly enabled local Markdown saving](DESKTOP.md#local-folder-paths-and-markdown-saving); old reference-only paths are not automatically enabled. Neither route changes the API cloud connector or Markdown export's write-permission requirements.

## Public APIs

```js
const connection = await connectCloud({ provider: 'google' | 'onedrive', clientId, tenant? });
// -> { name, load, save, verify, disconnect, connected, info, readOnly }
await connection.verify(); // checks current provider metadata; may create an empty OneDrive approot
connection.connected; // current access token has not expired; configuration alone is not connected
connection.info; // { accountType: 'personal' | 'business' | 'unknown', folder: null | { id, name, path, webUrl } }
await connection.load(); // -> { snapshot, revision: string } | null
await connection.save(snapshot, revision); // revision: string | null; -> new revision string
connection.disconnect(); // clears this in-memory connection
connection.readOnly; // Google: true only after authoritative content capability is false
await importMarkdownFiles(fileList); // -> { notes, folders }
await exportMarkdownFolder(snapshot); // -> number of non-deleted notes exported/already identical
downloadVault(snapshot); // downloads a validated complete JSON backup; returns undefined
```

Revisions are opaque strings; never manufacture one or reuse one from another file/provider/account. `null` authorizes creation only if there is no existing canonical snapshot. Connections throw actionable `Error`s, with `code` values such as `CLOUD_CONFLICT`, `CLOUD_AUTH`, `CLOUD_PERMISSION`, `CLOUD_READ_ONLY`, `CLOUD_PERMISSION_UNKNOWN`, `CLOUD_OFFLINE`, `CLOUD_DATA` and `CLOUD_REVISION` for UI handling. Cloud connections must be serialized by the caller/workspace; they are not automatic multiwriter transaction services.
