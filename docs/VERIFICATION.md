## Backend footprint

A throwaway load driver spawned the real HTTP/SQLite server in a separate child process, using a temporary data directory removed afterward. Server RSS below excludes the load-driver process. One workspace held 1,000 notes; serialized snapshot size was 657,817 bytes; reads were 20 serial authenticated requests over loopback, including JSON decoding by the client.

| Measurement | Observed value |
| --- | ---: |
| Spawn to listening | 109.3 ms |
| Server resident memory just after startup | 128.9 MiB |
| Server resident memory after setup, write and reads | 138.5 MiB |
| Mean full-workspace read | 5.20 ms |
| Slowest full-workspace read | 7.01 ms |

This is a sanity check, not a load/capacity benchmark. Windows/Node runtime mappings affect RSS; Linux container memory was not measured. Scrypt temporarily consumes additional memory; four simultaneous password derivations are allowed. No minimum-RAM guarantee is inferred from this run.

**Lightest deployment:** an installed personal PWA needs no running NitroBison backend; the initial static host can be any static-file server. **Small-group deployment:** one Node process and one SQLite data directory, with no installed production server dependencies or separate services. Node is the lowest-complexity shared-JavaScript choice here, not a claim of the smallest possible runtime. A Go/Rust binary or Python standard-library server could use less memory; those alternatives were not implemented or benchmarked.
